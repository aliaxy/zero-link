# AGENTS.md

This file is the canonical development guide for AI coding agents working in this repository.

## Project State

zero-link has completed Stage 2 API/RPC skeleton development and now has the Stage 3 backend management
implementation in place.

The repository intentionally has:

- Generated go-zero API and RPC services.
- API route contracts for health, readiness, administrator authentication, and short-link management.
- RPC methods for readiness, administrator authentication, and short-link management.
- Stage 3 foundation schema and generated MySQL models for administrator and short-link storage.
- JWT-based administrator authentication.
- MySQL-backed short-link create, list, detail, update, and soft-delete management logic.
- Local httpyac smoke request assets under `tests/httpyac/`.

Do not add redirect serving, Redis redirect cache behavior, analytics, management UI, new migrations, or
additional business contracts unless the user explicitly asks for that implementation stage.

## Repository Layout

- `docs/`: product, architecture, engineering, workflow, and planning documents.
- `deploy/`: deployment and local infrastructure assets. Local Docker Compose files belong here.
- `etc/`: root-level example and local configuration files.
- `services/link-api/`: go-zero HTTP API service.
- `services/link-rpc/`: go-zero RPC service.
- `migrations/`: versioned SQL migrations. Stage 3 currently includes the initial administrator and short-link schema.
- `tests/httpyac/`: local HTTP smoke requests and example httpyac variables.
- `web/admin/`: reserved for the future embedded admin UI.

## Development Rules

- Preserve the current Stage 3 management boundary unless the user explicitly asks for the next implementation stage.
- Do not run `goctl` generation unless the user explicitly asks for generated go-zero services.
- Do not handwrite code that should be generated by go-zero.
- Do not add redirect API contracts, redirect RPC methods, analytics APIs, management UI code, or additional migration SQL unless requested.
- Keep documentation in English.
- Prefer documentation-first changes when project intent or architecture changes.
- Keep changes small and scoped.

## Configuration Rules

- Every committed configuration file should have an example variant.
- Use `.env.example` for committed environment variable documentation.
- Use `.env.local` for machine-local environment values. Do not commit it.
- Use `etc/<service>.example.yaml` for committed service configuration examples.
- Use `etc/<service>-local.yaml` for machine-local service configuration. Do not commit it.
- Keep secrets and machine-specific values in ignored local files only.

## Go And go-zero Rules

- The Go module path is `github.com/aliaxy/zero-link`.
- If the module ever needs to be recreated, use `go mod init`; do not handwrite `go.mod`.
- Future service names are `link-api` and `link-rpc`.
- Future go-zero services should use generated `ServiceContext` wiring.
- RPC generation must be run from the repository root with:

```bash
goctl rpc protoc services/link-rpc/proto/link/v1/link.proto \
  --go_out=services/link-rpc/pb \
  --go_opt=paths=source_relative \
  --go-grpc_out=services/link-rpc/pb \
  --go-grpc_opt=paths=source_relative \
  --zrpc_out=services/link-rpc \
  --proto_path=services/link-rpc/proto
```

- Proto files should use absolute `go_package` values without explicit Go package aliases, such as `github.com/aliaxy/zero-link/services/link-rpc/pb/linkv1`.
- Accept goctl-generated package names, client directories, and exported client identifiers as the source of truth.
- Do not introduce a dependency injection framework unless explicitly requested.
- Keep Docker Compose application service integration for a later stage; local infra is separate.
- Readiness checks may use simple dependency connectivity checks and must not depend on business data.

## Local Infrastructure

Use:

```bash
make infra-up
make infra-down
```

The local infrastructure Compose file is:

```text
deploy/docker-compose.infra.yml
```

This file should provide local dependencies only. Do not add application services to it unless requested.

## Verification

Run:

```bash
make test
```

Validate the Compose configuration with:

```bash
docker compose -f deploy/docker-compose.infra.yml config --quiet
```

The repository now has Go packages, so `make test` should run the available unit tests when Go is available.

## Git Rules

- Do not make task changes directly on `main`.
- Create a task branch from `main` before implementation work.
- Choose branch prefixes by task type, such as `docs/`, `chore/`, `feat/`, `fix/`, or `ci/`.
- Example branch names:
  - `chore/config-example-local`
  - `docs/update-local-development`
  - `feat/link-redirect`
  - `fix/cache-invalidation`
  - `ci/add-github-actions`
- Before creating any commit, show the intended staged changes and commit message, then wait for explicit user confirmation.

Use Conventional Commits without emoji.

Format:

```text
<type>(<scope>): <subject>
```

Examples:

```text
docs: add agent development guide
chore(project): add service skeleton directories
chore(deploy): add local infra compose file
```

For the full workflow, see `docs/17-git-workflow.md`.
